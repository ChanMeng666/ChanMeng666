# Surfaces

Same facts, different register, different budget, different gate. This is the
lookup table for step 2 of the workflow: *which surfaces does this fact earn, and
what are that surface's rules?*

**The load-bearing distinction is edit-vs-generated.** Hand-editing a generated
file is the single most common way to lose work in this repo — the next build
silently reverts it.

| Surface | Edit or generated | Gate |
|---|---|---|
| `data/profile/*.yaml` | **edit** — the only source of facts | `validate`, `check:freshness` |
| `README.md` | generated by `scripts/build.mjs` | CI diffs the committed output |
| `llms.txt`, `llms-full.txt`, `dist/profile.json` | generated | CI diffs the committed output |
| `public/cv-llms.txt`, `public/cv.jsonld` | generated (mostly — see below) | CI diff |
| `cv/sections/*.typ` | **edit** — hand-curated prose | `check:cv --strict` (anchor facts only) |
| `cv/chan-meng-cv-ats.typ` | **edit** — hand-curated prose | `check:cv --strict` + `check:ats` (shape + counts) |
| `cv/exports/*.{pdf,docx,txt}` | generated from the `.typ` | `verify-ats-exports.py` (manual, not CI) |
| `cv/extended.typ` | **edit** | none — prose only |
| `data/profile/70-linkedin.yaml` | **edit** — LinkedIn display copy | `check-linkedin-sync` (fact mapping only) |
| `linkedin/*.{json,md}` | generated | — |
| `cv/cover-letter/*.md` | **edit** — a kit, not a document | none |
| `chanmeng.org` (`D:/github_repository/2d-portfolio`) | separate repo; PDFs copied in by hand | none — see the sync rule below |

Every hand-edited surface above is covered by `npm run check:copy`.

---

## `data/profile/*.yaml` — the source

**Register:** neutral, complete, over-specified. This is the only place a fact is
allowed to originate, and the only place a number is allowed to first appear.
Write more than any single surface needs; the surfaces select from it.

**Rules that matter downstream:**

- A number that is not here fails `check:copy` R8 on every other surface.
- `narrative.impactHeadline` is what the CV and the GEO surfaces draw their
  one-line claim from. It should lead on business outcome, never on commit counts
  or solo percentages.
- `publicSummary` is the lay-reader version — plain language, no jargon that a
  recruiter would have to look up.
- `tagline` is the dense engineer-facing version.
- No pricing or cost framings in project narratives.
- Cross-references (`relatedWorkId`, `clientOrgId`, `spotlightProjectIds`, …) are
  listed in `CLAUDE.md` and are not all schema-enforced. Keep them true by hand.

## The designed two-page CV — `cv/sections/*.typ`

**Register:** narrative, outcome-first, human-facing. This is the document a
person reads, not a parser.

**Budgets, all hard:**

| Section | Budget |
|---|---|
| Total | **2 pages**, with no slack |
| Experience | **5** detailed roles; everything else compresses into the italic "Previously:" run-on |
| Selected Projects | **5** cards, 1–2 bullets each |
| "What I Bring to a Team" | **5** bullets |
| Recognition | **4** bullets |

**Rules:**

- **No summary opens with a duty verb.** Every summary carries at least one
  verifiable business-outcome metric.
- **No commit counts, no solo percentages.** They measure typing, not the problem
  solved. Where ownership is load-bearing, say it in words — *sole engineer*,
  *built it solo*, *still operate it*.
- **No card duplicates a role.** A product built at an employer is named in
  Experience and not re-described in Projects.
- Each "What I Bring" bullet leads on what the *reader* gets, then backs it with
  one concrete technical signal. The signal half must actually support the
  promise half — an evaluation harness does not make spend predictable.
- Every tool and project appears **exactly once** across the whole document.

**Before editing any `.typ`:** read `cv/TYPST_PITFALLS.md`. Eight non-obvious
layout bugs are already fixed there and must not be reintroduced.

## The ATS resume — `cv/chan-meng-cv-ats.typ`

**Register:** action-verb bullets, expanded acronyms, machine-legible. This is the
**default upload**. It is deliberately *not* symmetrical with the designed CV —
Sanicle, Engram, ByteDance, CORDE and Forward with Her are full dated entries
here and prose mentions there, because a parser cannot extract employment from
prose. **Do not "reconcile" the two.**

**Counts, all hard-asserted by `scripts/lib/parse-ats-resume.mjs` — every one
throws, none warns:**

| Thing | Count |
|---|---|
| Section headings, exact strings, in order | 7 |
| Roles | 10 (7 with bullets, 3 compact) |
| Bullets total (`verify-ats-exports.py`) | 11 |
| Projects | 5 |
| "Also built" links | 4 |
| Education | 2 |
| Awards | 3 |
| `skills-line` rows | 5 under skills, 2 under certifications |
| Contact lines | 2 |
| Extracted characters | **6,800–9,000** |
| Pages | **2** |

Changing any count means changing `EXPECT` in that parser — which is fine, but it
is a deliberate, recorded change, not a workaround. **The document currently sits
with under one line of slack at two pages.** Adding anything means deciding what
comes out first.

**Prose rules:** one sentence per bullet; if it grows to two, split it or trim it
— never cut the metric. Three-letter months. Commas, never spaces, between list
items. No bare ` - ` mid-sentence (it extracts as a space). No italics.

The full hard-rule list — fonts, margins, hyphenation, tagging, why each was
chosen against measured extractor behaviour — is in `cv/README.md` § "ATS variant
— hard rules". Read it before touching layout.

**After any content edit:** bump `date: datetime(...)` by hand (it is the
document's revision date, not a build timestamp), then run
`python cv/verify-ats-exports.py`. That verifier is **not in CI** — the document
drifted to three pages unnoticed for three weeks once.

## The extended CV — `cv/extended.typ`

**Register:** first person, present tense, magazine. 16 pages. This is the brand
document, not the hiring document — it opens by saying so and points at the
two-page CV.

**Rules:**

- **Caption truth.** A caption describes only what is actually visible in that
  frame. Captions have been wrong here before — a photo captioned "Auckland" that
  showed a boat at sea in Cebu.
- Life detail earns its place only when it bridges to product taste or technical
  judgement. Otherwise cut it.
- No commit counts or solo-percentage bragging in prose; product feature counts
  (`355 templates`) are fine.

## LinkedIn

See [`linkedin.md`](linkedin.md) for the doctrine. The caps are LinkedIn's, they
are hard, and it truncates silently past them — `check:copy` R9 enforces them:

| Section | Cap | Leads with |
|---|---|---|
| Headline | **220** | The value clause, then searchable keywords |
| About (lead + sections) | **2,600** | How you help, before what you achieved — and the hook must clear the ~300-char "See more" fold |
| Experience entry, per position | **2,000** | The career narrative |
| Projects entry | **2,000** | The artefact |

Remember the pipeline is inverted: `70-linkedin.yaml` is the source and
`linkedin/*.{json,md}` are generated. Dates, titles and award metadata are
injected from the canonical sections and must not be duplicated in the
`linkedin:` block. A display title that deliberately differs from
`work[].position` needs `_titleCurated: true`.

## Cover letters — `cv/cover-letter/`

Not a document; a kit. `TEMPLATE.md` is a five-move skeleton, `EVIDENCE.md` is a
bank of pre-written, source-attributed sentences grouped into seven themes.

**Rules:** 220–320 words total. Two evidence moves, from **two different themes**
— a second latency number after a first latency number adds nothing. Every
factual sentence traces to `data/profile/`. No superlative without an enumerable
comparison set. No claim that a team's result was yours.

`EVIDENCE.md` opens with **six red lines** — six statements a reference check
would contradict. Read them before writing anything public. They are not style
notes.

## The GEO sidecars — `public/cv-llms.txt`, `public/cv.jsonld`

**Register:** compact, machine-first. `cv-llms.txt` exists to be small enough
that a sourcer LLM can hold the whole thing in one prompt alongside a job
description — **keep it under ~200 lines**. `cv.jsonld` is schema.org Person +
WorkExperience for recruiter LLMs that parse structured data directly.

Both are generated from the shards, with one deliberate exception:
`cv/build-llms-txt.mjs` keeps ~25 hardcoded lines of Claude-Code-ecosystem
architect vocabulary (hub-and-spoke coordinators, `PostToolUse` hooks,
`stop_reason`-driven loops, the anti-patterns rejected). That vocabulary
describes the repo's own engineering practice, has no shard home by design, and
is the only thing making this file non-redundant with `llms.txt`. Everything else
in it must come from YAML.

> `[verified]` Before 2026-09-07 this file hardcoded ~120 lines and was gated by
> nothing. It published a **zero-downtime** migration claim the shard contradicts
> (`~30 min downtime`), a credential ID against the wrong certificate, a role as
> current that had ended, and attendance wording for a conference Chan attended
> by video link — the exact thing red line #2 forbids. An ungated copy surface
> does not stay true; it only stays quiet.

## The site — `chanmeng.org`

`public/chan-meng-cv.pdf` and `public/chan-meng-cv-extended.pdf` are **also**
served from a separate repo, `D:/github_repository/2d-portfolio/public/`, and
nothing syncs them.

**A CV rebuild is not finished until the site is synced.** Copy exactly those two
files, **bump `PREVIEW_V` in `src/app/cv/page.tsx` in the same commit**, and
push — push is the deploy. Each Cloudflare colo caches for four hours
independently, so new bytes behind an unchanged URL render the *previous* CV,
look completely fine, and are wrong. That is the only failure here whose symptom
is invisible.

Never copy anything out of `cv/exports/` to the site. Those are the ATS
artifacts, and the reason they live outside `public/` is that no crawler should
find a second, competing "current CV".
